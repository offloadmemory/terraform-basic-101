# Terraform Concepts, Explained Simply

This is the "what does this word mean" document. Read it once, keep it open,
and look things up when a command or error mentions a term you don't know.
Every section maps to real code in this repository.

---

## 1. Infrastructure as Code (IaC)

**Instead of** clicking around the AWS console to create a VPC, a database,
or a load balancer, **you write a text file that describes them**. Terraform
reads the file, compares it to what already exists in AWS (the *state*), and
makes the cloud match your file.

> The golden rule of IaC: **if it isn't in the code, it doesn't exist.**
> Anyone (or any robot) can re-create your entire infrastructure from the
> files in this repo. That is the superpower.

## 2. Providers

A provider is a plugin that lets Terraform talk to a specific cloud. AWS,
Azure, GCP, Kubernetes, GitHub… each has one. In this repo every
configuration has a `providers.tf`:

```hcl
provider "aws" {
  region  = var.region
  profile = var.profile
}
```

The `required_providers` block in `terraform.tf` says *which* provider and
*which version*:

```hcl
required_providers {
  aws = {
    source  = "hashicorp/aws"
    version = "~> 6.28"
  }
}
```

- `source = "hashicorp/aws"` — the official AWS provider, from HashiCorp.
- `version = "~> 6.28"` — "any 6.x version from 6.28 up". Pinning versions
  means everyone in your team gets the same behaviour.

## 3. Resources

A resource is one concrete thing Terraform creates: an S3 bucket, a VPC, an
RDS instance, a security group. Resources are what `terraform apply`
creates, and what `terraform destroy` removes.

**This repo creates very few resources directly** — it delegates almost all
of them to modules (section 5). That is the whole point of the "basic" repo.

## 4. Modules

A module is a **reusable, packaged bundle of resources**. Instead of
hand-writing 200 lines of VPC code, you say:

```hcl
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 6.7.0"

  name = var.vpc_name
  cidr = var.vpc_cidr
  # ...a handful of inputs
}
```

Modules are the "functions" of Terraform: you give them **inputs**
(`cidr`, `azs`…), and they create a set of resources and hand back
**outputs** (`vpc_id`, `public_subnets`…).

The magic of this repo: **every module is downloaded from the Terraform
Registry**, the official public library of vetted modules
(<https://registry.terraform.io>). The `terraform-aws-modules` namespace is
maintained by the community and used by thousands of companies. You write
~10 lines and get a production-grade VPC — without ever seeing the internals.

> Local modules (code you keep in the repo) are the *other* way to do it —
> that is what `terraform-101` does. This repo deliberately skips them to
> stay simple. When you write your own module later, it is "just" a folder
> with `main.tf` / `variables.tf` / `outputs.tf` that other code calls —
> exactly like these registry modules, but local.

## 5. Variables

Variables are the input knobs of a Terraform configuration. Declared in
`variables.tf`:

```hcl
variable "vpc_cidr" {
  description = "CIDR block for the VPC"
  type        = string
}
```

Values are provided in `terraform.tfvars`:

```hcl
vpc_cidr = "10.0.0.0/16"
```

Rules of thumb (they are enforced by tflint in CI):
- every variable gets a `description` and a `type`;
- secrets never go into variables as plain text (our DB password is
  generated by AWS, see `docs/CONCEPTS.md` section on state).

## 6. Outputs

The "return values" of a Terraform configuration. When you run `terraform
output`, these are what you get:

```hcl
output "vpc_id" {
  description = "ID of the VPC"
  value       = module.vpc.vpc_id
}
```

Outputs marked `sensitive = true` (like the database endpoint) are hidden
from `terraform output` unless you ask for them explicitly — good hygiene
for anything that smells like a credential.

## 7. State — the most important idea

Terraform keeps a **state file** for every configuration. The state is
Terraform's memory of what it created:

- it knows resource A in AWS is `aws_s3_bucket` with id `x`;
- next run, it reads state, compares to AWS, and computes the **diff**;
- the diff decides what to create / update / delete.

State files **can contain secrets** (a database endpoint, an access key
that leaked into a resource attribute) — that is why:

1. state is stored in a **private S3 bucket** (never on a laptop or in a
   repo),
2. that bucket has versioning + encryption + public access blocked,
3. `*.tfstate*` is in `.gitignore` (never commit state!),
4. we keep everything in **one** configuration so modules reference each
   other directly — no cross-state reads at all (sections 8–9).

### Local vs remote state

- **bootstrap** (`infra/bootstrap`) uses **local state** (a file on your
  disk). It must, because the S3 bucket doesn't exist yet — the
  chicken-and-egg of section 10.
- **infra** (the whole stack) uses **remote state** in the S3 bucket.

### Locking

When two people run `terraform apply` at the same time, both could overwrite
state and break everything. Terraform's S3 backend solves this with a
**lock file**: the first run creates `.tflock` in the bucket, the second run
fails with `Error: acquiring the state lock` until the first finishes. See
TROUBLESHOOTING for the exact error.

## 8. Data sources

A data source is a **read-only** query — Terraform fetches something that
already exists, without changing it.

> **Rule of thumb:** resources create things; data sources read things.

**This repository uses no data sources at all** — and that is deliberate.
In a multi-workspace repo, `database` and `ecs` would need values from the
`network` *workspace* (subnet IDs, VPC ID) and would fetch them from its
separate state file:

```hcl
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket  = "terraform-basic-101-tfstate"
    key     = "dev/network/terraform.tfstate"
    region  = "us-east-1"
    profile = "dev"
  }
}
```

That is the *fragile* way — if the network state file is ever deleted, the
database breaks. Here, everything lives in **one configuration**, so the
database and ECS just reference the VPC module's outputs directly:

```hcl
# database.tf — no data source, no state-file read
subnet_ids = module.vpc.private_subnets
```

Same result, nothing to break. (`terraform-101` shows the enterprise
alternatives: Terragrunt `dependency` blocks, or publishing outputs to SSM.)

## 9. One configuration — one folder, one state

Terraform has a feature literally called *workspaces* — but the enterprise
standard (and this repo) doesn't use it for environments. Instead: **one
folder per configuration = one independent Terraform root = one state
file**.

Why folders instead of `terraform workspace`? HashiCorp's own guidance says
it: environments differ not just in *values* but in *state isolation,
access, and blast radius*. A separate folder makes it impossible to
accidentally run a dev plan against prod state. It's simpler to teach and
safer to run.

This repo goes one step further: even *within* the single environment there
is exactly **one** configuration (`infra/`). The resources are split by
concern into `network.tf`, `database.tf`, `ecs.tf` — but they are one
config, one `terraform init`, one state file. That is the "file-based"
structure: the same readability as separate workspaces, but a single apply
that orders everything itself.

If you later want a `staging` and `prod`:
1. copy `infra` → `staging-infra`,
2. change the state bucket key + profile + tfvars,
3. done — no code changes.

That is the *promotion story* that `terraform-101` demonstrates with three
environments. This repo deliberately shows just one so the pattern is
obvious.

## 10. The bootstrap chicken-and-egg

`infra/backend.tf` points at the S3 bucket `terraform-basic-101-tfstate`.
But **you can't run Terraform against a bucket that doesn't exist yet**.
Something must create the bucket first — that is `infra/bootstrap`, which
has **no backend at all** and keeps its state locally.

```
bootstrap (local state)  →  creates the bucket  →  everything else uses it
```

That's why the quick start always starts with bootstrap.

## 11. The 4 command lifecycle

| Command | What it does | When you run it |
|---|---|---|
| `terraform init` | Downloads providers + modules, sets up the backend | Every time you clone the repo / change the backend |
| `terraform plan` | Compares state vs. code, shows the diff. **Nothing changes.** | Before every apply — this is your safety check |
| `terraform apply` | Makes AWS match the code | When you're happy with the plan |
| `terraform destroy` | Deletes every resource the code created | Demo over. Seriously. It costs money. |

## 12. Quality gates (why CI + pre-commit)

Even in a basic repo, three free tools keep you honest:

- **`terraform fmt`** — canonical formatting. One style, everywhere.
- **`terraform validate`** — syntax + type checks (needs no credentials).
- **`tflint`** — a linter that catches AWS-specific mistakes: wrong instance
  classes, missing version pins, public SGs.

They run locally on every commit (`.pre-commit-config.yaml`) and on every
pull request (`.github/workflows/ci.yml`). If you want to be a DevOps
engineer, make gates like these a habit from day one — that's the standard
`terraform-101` demonstrates at enterprise scale.
